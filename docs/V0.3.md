# V0.3 — Verification / Retry / Reviewer

V0.3 把 V0.2 的模型路由升级成有验证和失败闭环的执行流程。

## 关键语义说明

V0.3 的 `LOW → MEDIUM → HIGH` 不是“故意先用弱模型试错”。正确含义是：

```text
第一次：根据任务真实难度直接分配对应档位
失败后：把真实失败视为初始难度估计可能偏低的证据，再向上重新分类
```

因此：

```text
LOW task    → LOW
MEDIUM task → MEDIUM
HIGH task   → HIGH

LOW failure    → MEDIUM
MEDIUM failure → HIGH
HIGH failure   → HIGH retry / BLOCKED
```

基础设施、权限、缺少凭据、限流、网络、工具不可用等失败不属于“任务难度估计错误”，不应因此升级模型。

## 执行闭环

```text
Executor
   ↓
Checker
   ↓
失败？ ── yes ──→ Reclassify upward
   │                    ↓
   │                  Retry
   │                    ↓
   │                 BLOCKED
   ↓ no
Reviewer（可选）
   ↓
PASS
```

## Retry / Escalation 示例

```yaml
- id: implement-parser
  title: Implement parser
  kind: normal_code
  max_attempts: 3
  escalate_after: 1
  prompt: Implement the parser and keep existing behavior compatible.
```

如果初始分类是 `MEDIUM`：

```text
attempt 1 → MEDIUM
attempt 2 → HIGH
attempt 3 → HIGH
```

如果初始分类已经是 `HIGH`，失败不会再凭空出现更高档位，而是继续 HIGH 或进入 BLOCKED。

为了兼容旧计划，Python Core 仍允许用户显式配置不同的 `escalate_after`；Plugin 主线从 V0.4 开始采用“真实模型失败后立即上调一个档位”的语义。

## Checker

Checker 是确定性 Gate，不依赖模型自己说“完成”。支持 Task `checks` 和可选 Git working-tree change Gate。

如果测试失败，记录 `CHECK`；如果 `require_diff` 开启但没有真实变化，记录 `DIFF`。

## Independent Reviewer

Reviewer 与 Executor 分离：

```text
EXECUTOR → CHECKER → REVIEWER
```

Reviewer 根据原任务、acceptance criteria 和 Checker evidence 给出机器可解析的 `PASS` / `FAIL`。Reviewer FAIL 也属于任务未通过，需要重新判断后续尝试是否应该升级。

## Manual Retry

```bash
autodev retry <task-id>
autodev retry <task-id> --run
```

人工 retry 重置本轮预算，但保留：

- `failures[]`
- `route_history[]`
- `retry_cycles`

## 状态

Workflow：`READY / RUNNING / PAUSED / FAILED / BLOCKED / PASSED`

Task：`PENDING / RUNNING / FAILED / BLOCKED / PASSED`
