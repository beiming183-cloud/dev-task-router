# V0.6 — GitHub Repository Context

V0.6 makes task decomposition and difficulty classification repository-aware without turning the project into a heavy server product.

## Core flow

```text
User goal
  ↓
Target GitHub repository / branch / PR
  ↓
Commit-anchored repository evidence
  ↓
Relevant files / tests / diff / CI only
  ↓
Project → Stage → Step → Task
  ↓
DifficultyClassifier
  ↓
Surface Router
```

The repository is used as a source of implementation facts. The user request still defines the desired target behavior.

## Plugin skill

New skill:

```text
plugins/dev-task-router/skills/inspect-repository/SKILL.md
```

It instructs the assistant to:

- resolve repository and target ref;
- anchor evidence to a commit SHA;
- search with task-specific symbols or error text;
- fetch only relevant implementation files and nearby tests;
- inspect relevant PR changed files/patches;
- inspect current CI/check state;
- fetch detailed CI logs only when a failing job matters;
- refresh evidence if the branch head moved;
- avoid fabricating GitHub facts when access is unavailable.

## RepositoryContext

The Python reference core adds `RepositoryContext`.

Example:

```yaml
source: github
repository: owner/repo
branch: feature/example
commit: abcdef123456
pr_number: 42
relevant_files:
  - src/input/cursor.py
  - src/input/selection.py
changed_files:
  - src/input/cursor.py
test_files:
  - tests/test_cursor.py
ci_status: failure
ci_checks:
  - pytest
evidence_tags:
  - core-state
facts:
  - Cursor and selection share the same state owner.
```

The snapshot can be stored as:

```text
.autodev/repo-context.yaml
```

CLI helpers:

```text
autodev repo-context --import repo-context.yaml
autodev repo-context
autodev repo-context --json
```

## Difficulty correction from repository evidence

Task text remains the first signal. Verified repository evidence can then correct the score.

Examples:

```text
1 relevant file, one module
→ no automatic inflation

2–3 relevant/changed files
→ small scope signal

4–7 files
→ multi-file signal

8+ files
→ broad-scope signal

2+ module roots
→ cross-module signal

verified auth / migration / core-state / public-api / compatibility tag
→ strong high-risk signal
```

A visually small change can therefore become HIGH when inspection proves that it crosses a high-risk semantic boundary.

A large repository does not make every task HIGH. Only the relevant scope is counted.

## CI semantics

CI state is evidence, not a generic difficulty multiplier.

- `success` helps verification and handoff.
- `failure` adds uncertainty mainly to debugging/review work.
- infrastructure failures must not be interpreted as proof that the coding task itself is harder.

## Handoff

The generated handoff now carries a compact repository section:

- repository;
- branch;
- commit;
- PR;
- CI/checks;
- relevant files;
- evidence tags;
- verified facts.

Default handoff budget is intentionally small. The next model should not receive a full repository dump or old chat history.

## Source-of-truth rule

Keep these separate:

```text
GitHub evidence = current implementation facts
User request    = desired target behavior
```

If they disagree, report the current fact and preserve the target request as work to perform.

## Current limits

V0.6 does not:

- add a server or database;
- automatically install/connect GitHub for the user;
- claim that a Skill can switch the active ChatGPT model;
- download or summarize an entire repository by default;
- execute multiple external model APIs yet.

The connected GitHub Plugin/App is the preferred evidence source when available. The Python core consumes the compact evidence snapshot rather than embedding GitHub credentials or API logic.

## Verification

V0.6 adds regression coverage for:

- repository context validation and safe paths;
- context compaction;
- broad-scope difficulty correction;
- localized work not being inflated;
- pseudo-simple high-risk changes;
- CLI import/show;
- workflow route traits;
- repository-aware handoff;
- Plugin manifest and repository-inspection Skill rules.
