# V0.9 — Execution Evidence / Recovery / Repository Sync

V0.9 builds on the V0.8 same-conversation execution loop. The goal is not to make the loop more aggressive; it is to make long-running local execution **recoverable, auditable, and fail-closed** when a process dies or durable state disagrees.

Windows ChatGPT live UIA calibration is still intentionally deferred. The recovery and evidence state machine is implemented and covered by automated regression tests, but real selectors/model-effort/composer/response controls are not claimed as live-verified on the user's machine.

## 1. Execution Evidence Ledger

Runtime evidence is written to:

```text
.autodev/execution-evidence.jsonl
```

The file is local runtime state and is ignored by Git.

Each event contains a compact payload plus an event hash linked to the previous event hash. This provides an append-only SHA-256 chain that can detect accidental or manual mutation of prior evidence.

The ledger is deliberately compact. It stores identifiers, status, digests, route/check facts, and recovery decisions; it does **not** replay the full ChatGPT conversation.

Typical model-task evidence progresses through boundaries such as:

```text
PREPARED
→ SUBMITTED
→ RESPONSE_COLLECTED
→ CHECKED
→ STATE_RECORDED
```

Deterministic NONE execution also emits evidence, while keeping NONE failure semantics separate from model Difficulty promotion.

## 2. PREPARED / ambiguous-send recovery

`LocalRecoveryController` reconciles the most dangerous crash boundary: a session exists, but the process may have died before or after the UI send click.

The dispatch ledger reservation is written before attempting Send. Therefore:

```text
PREPARED + no dispatch reservation
→ SAFE_RETRY
```

This is the one case where a new send can be proven safe without UI evidence.

If the dispatch ledger already says `submitted`:

```text
PREPARED + submitted
→ RESUME
```

The existing dispatch is resumed and must not be sent again.

For sticky `submitting`:

```text
submitting + calibrated post-baseline response activity
→ submitted
→ RESUME
```

If no post-baseline activity can be verified, the result remains:

```text
AMBIGUOUS
```

The system blocks instead of guessing and risking a duplicate send.

## 3. Later crash-point recovery

V0.9 also covers later durable-write ordering failures.

Examples:

- response text is already on disk but session metadata was not updated before the process died;
- Checker state was written, but the session did not reach its terminal status;
- workflow state already records the matching `local_dispatch_id` and terminal result while the session still reports `CHECKED` or `REVIEW_REQUIRED`.

Recovery uses durable file/state facts to reconcile forward. Replaying the same dispatch must not increment attempts again, append duplicate failure history, or create another send.

## 4. Evidence and consistency audit

New CLI commands:

```text
autodev-local evidence --json
autodev-local evidence --dispatch-id <id> --json
autodev-local audit --json
```

`evidence` verifies the append-only hash chain and displays compact execution events.

`audit` cross-checks durable state, including:

- evidence chain validity;
- response-file SHA-256 versus session metadata;
- session task/dispatch identity versus dispatch ledger;
- workflow `local_dispatch_id` versus local session/evidence;
- terminal workflow state versus recoverable session state.

Recoverable lag can be reported as a warning. Data corruption, digest mismatch, or incompatible identities are errors and fail closed.

## 5. Independent Reviewer boundary

V0.8 stopped at `REVIEW_REQUIRED`. V0.9 makes the independence condition explicit.

The same canonical ChatGPT conversation cannot be treated as an independent reviewer simply by sending another prompt that says "review independently".

Automatic review requires explicit local reviewer configuration and an allowed external executor/command path. Defaults remain disabled.

The distinction is important:

```text
reviewer verdict FAIL
→ genuine task verification evidence
→ may drive the implementation retry policy
```

but:

```text
reviewer executable missing
reviewer transport/process failure
reviewer output protocol failure
→ infrastructure failure
→ do not consume a new implementation attempt
```

The independent-review policy is fail-closed.

## 6. Repository execution evidence synchronization

A local Checker PASS is not a remote GitHub fact.

V0.9 adds strict repository-anchor synchronization. Rolling `last_commit` can move only when all required evidence agrees:

```text
RepositoryContext has concrete commit
+ RepositoryContext CI == success
+ local Git HEAD == RepositoryContext commit
+ relevant local worktree is clean
```

CLI:

```text
autodev-local sync-repository --json
```

If the commit differs, CI is not successful, or the local worktree still contains business changes, the old anchor remains unchanged.

This prevents an uncommitted local implementation from being recorded as if it were already verified on GitHub.

## 7. Failure semantics remain stable

Recovery does not weaken the existing routing rules.

Infrastructure states such as UI selector drift, ambiguous Send, response timeout, evidence inconsistency, missing reviewer transport, or GitHub synchronization failure do **not** increase Task Difficulty.

Only a completed model attempt that reaches objective CHECK/DIFF/reviewer verification and fails can provide promotion evidence:

```text
LOW failure    → MEDIUM
MEDIUM failure → HIGH
HIGH failure   → HIGH retry / BLOCKED
```

Deterministic command failure remains:

```text
NONE failure → DEBUG_TASK_REQUIRED
```

The failed NONE command is not silently converted into a model task. Debugging must be represented as a separate task and classified independently.

## 8. CLI summary

Existing V0.8 execution commands remain:

```text
autodev-local prepare --json
autodev-local gate --dry-run --json
autodev-local probe-conversation --json
autodev-local run --json
autodev-local resume --json
autodev-local continue --max-cycles 10 --json
```

V0.9 adds:

```text
autodev-local recover --json
autodev-local evidence --json
autodev-local audit --json
autodev-local sync-repository --json
```

Recommended recovery order:

```text
audit
→ evidence
→ recover when PREPARED/ambiguous
→ resume existing dispatch
→ Checker / independent Reviewer
→ refresh GitHub RepositoryContext + CI
→ sync-repository when anchors match
→ continue
```

The Skill documents conservative PREPARED reconciliation, evidence/audit commands, independent-review requirements, repository-anchor synchronization, and the truthfulness boundary for uncalibrated Windows UIA.
