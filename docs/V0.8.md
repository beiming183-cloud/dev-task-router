# V0.8 — 本地同会话自动执行闭环

V0.8 从 V0.7 的 Same-Conversation Foundation 继续，把 Task Context Pack、难度路由、本地 exact mode switch 契约、当前会话发送、响应收集和 Checker 串成一条可恢复的执行链。

```text
Task Ready
→ refresh rolling/repository context
→ Task Context Pack
→ Difficulty / requested profile
→ verify actual profile
→ current canonical ChatGPT conversation
→ safe submit
→ response completion monitor
→ Checker / Git evidence
→ PASS / real failure evidence
→ rolling context delta
→ next Task
```

V0.8 的 Windows UIA 驱动已经实现，但用户当前选择暂缓真实 ChatGPT Windows 客户端校准。因此默认配置仍关闭，本版本只声称：**代码路径和自动回归已实现，真实客户端尚未 live-verified。**

---

## 1. 发送前硬门禁

`LocalConversationOrchestrator.prepare()` 生成 `LocalExecutionEnvelope`：

```text
Task / Stage / Step
Difficulty
Task Context Pack
requested profile
deterministic flag
```

每次准备新模型 Task 前都会重新读取：

```text
.autodev/context.yaml
.autodev/repo-context.yaml
.autodev/models.yaml
.autodev/surfaces.yaml
```

因此长时间运行不会一直使用进程启动时的旧 Context Pack。

模型 Task 遇到以下状态全部 fail closed：

```text
STALE_CONTEXT
ROUTE_UNRESOLVED
MODE_SWITCH_UNAVAILABLE
MODE_SWITCH
PROFILE_MISMATCH
```

只有：

```text
context valid
+ requested profile resolved
+ switch verified: true
+ actual family/effort == requested family/effort
```

才允许进入当前 canonical conversation。

这些基础设施失败都不会增加模型 `attempts`，也不会触发 Difficulty promotion。

## 2. 当前会话安全发送

`WindowsUIAConversationBackend` 只操作当前可见 ChatGPT conversation，不选择另一个聊天窗口，也不依赖固定屏幕坐标。

提交前顺序：

```text
find current ChatGPT window
→ find calibrated composer
→ insert full Task Context Pack
→ read back full composer text
→ require exact match
→ find calibrated Send control
→ duplicate ledger check/reserve
→ submit
```

运行时 duplicate ledger：

```text
.autodev/local-dispatch.json
```

`submitting` 状态故意保持 sticky。若进程刚好在点击 Send 的模糊边界崩溃，下一次宁可阻塞，也不会自动发送第二条相同消息。

重复检查发生在碰 UI 之前；这样即使第二次运行时 ChatGPT UI 已变化，duplicate guard 也不会被 selector 错误掩盖。

## 3. Response Monitor

响应采集配置位于 `.autodev/local-conversation.yaml` 的 `response` 节，默认：

```yaml
response:
  enabled: false
  busy_labels: []
  busy_control_types: [Button]
  assistant_control_types: [Text, Document]
  assistant_automation_id_regex: ""
  poll_interval_seconds: 1.0
  timeout_seconds: 900.0
  stable_polls: 2
```

启用响应采集时必须提供明确的 `assistant_automation_id_regex`；空正则不会被解释成“匹配所有 UI 控件”。

发送前 baseline 只保存：

```text
assistant message count
+ SHA-256(latest assistant message)
```

不会把整段旧聊天保存进状态文件。

完成判定采用保守语义：第一次看到新文本只建立 candidate；之后还需要 `stable_polls` 次额外、完全不变的确认，并且没有 busy indicator，才算 response completed。这样能避免流式生成中短暂停顿被误判成结束。

响应超时、selector 失效、UI 读取失败都属于 infrastructure failure：

```text
attempts 不增加
Difficulty 不升级
Task 不重发
```

## 4. 可恢复 Local Session

V0.8 使用：

```text
.autodev/local-sessions.json
.autodev/local-responses/<dispatch_id>.txt
```

保存最小恢复元数据。旧 conversation 不写入 session ledger；收集到的本次 assistant response 单独存文件并记录 SHA-256。

主要状态：

```text
PREPARED
SUBMITTED
WAITING_RESPONSE
COLLECTED
CHECKED
REVIEW_REQUIRED
PASSED
CHECK_FAILED
FAILED
BLOCKED
```

### 超时恢复

若消息已经发送但 response 尚未稳定：

```text
SUBMITTED
→ WAITING_RESPONSE
```

此时模型 `attempts` 仍为 0。

再次运行 `resume`：

```text
继续等待同一个 dispatch_id
```

不会再发送一次 Task。

若根本不存在 active session：

```text
autodev-local resume
→ NO_ACTIVE_SESSION
```

并明确拒绝创建新的 dispatch。

### CHECKED crash recovery

如果 Checker 已运行，但进程在最终状态落盘边界中断，`dispatch_id` 用作幂等键；恢复时不会再次增加 `attempts` 或重复追加同一 failure。

## 5. Checker 才决定 Task 是否完成

三种事件都不等于 PASS：

```text
ChatGPT 接受消息 ≠ PASS
ChatGPT 回答完成 ≠ PASS
模型文字声称“完成” ≠ PASS
```

只有收集到完整 response 后才进入：

```text
Task checks
Git diff requirement
independent review requirement
```

对于 `require_diff`，发送前保存的是 Git snapshot 的 SHA-256 digest，而不是整份 diff snapshot，因此 WAITING_RESPONSE 恢复不需要把巨大 Git 内容常驻 session state。

只有真正完成一次模型执行并进入 Checker/DIFF 验证后，失败才计入一次模型 attempt。

因此：

```text
MEDIUM model response
→ CHECK failure
→ attempts += 1
→ next real model run may route HIGH
```

而 UI / response timeout 不会造成这种提升。

---

## 6. Review boundary

`review: true` 的 Task 在 Checker PASS 后进入：

```text
REVIEW_REQUIRED
```

不会直接 PASS。

当前同一个 ChatGPT conversation 不被伪装成“独立 reviewer”。真正独立 Review 需要后续单独 execution/reviewer 通道，因此 continuous loop 在此停止。

---

## 7. Rolling Context 增量更新

客观 PASS 后，只自动写入机器确定的事实，例如：

```text
Verified PASS <task-id>
Checker verified
short dispatch id
```

同 stage 的下一 Task 会读取这条 stage PASS fact。

不会从 assistant response 自由文本里自动提炼：

```text
durable decision
protected constraint
architecture truth
```

这样可以避免一次模型幻觉永久污染后续项目上下文。

`last_commit` 也不会因为本地 Task PASS 就自动前移；只有新的 repository evidence anchor 才应该更新 commit-sensitive truth。

PASS 后同步刷新 `handoff.md`。

---

## 8. Deterministic NONE

真正的确定性 Task：

```text
kind=test/build
+ known command
+ no reasoning prompt
```

不会进入 ChatGPT conversation。

成功路径：

```text
NONE command
→ checks
→ PASS
→ rolling context verified fact
→ next Task
```

失败路径：

```text
NONE command failure
→ DEBUG_TASK_REQUIRED
→ stop
```

失败后不会：

```text
NONE → LOW
NONE → MEDIUM
NONE → HIGH
```

同一个失败 command 再次调用也不会自动重跑。必须创建独立 debug Task，并按 debug 内容重新分类。

## 9. Continuous project loop

单个 Task：

```text
autodev-local run --json
```

只恢复已经发出的模型 Task：

```text
autodev-local resume --json
```

连续执行：

```text
autodev-local continue --max-cycles 10 --json
```

Continuous loop 可以自动跨过：

```text
PASSED
CHECK_FAILED → promoted retry
successful deterministic NONE
```

遇到下列状态立即停止：

```text
WAITING_RESPONSE
RECOVERY_REQUIRED
REVIEW_REQUIRED
DEBUG_TASK_REQUIRED
FAILED / BLOCKED
context / mode / UI infrastructure failure
```

`--max-cycles` 是硬上限，防止异常状态形成无限执行循环。

低层 `autodev-local dispatch` 仍保留作诊断工具，但它不管理 response/checker session，不应作为正常项目 runner。

## 11. 自动验证状态

截至本阶段，GitHub Actions 自动回归：

```text
89 passed
```

覆盖包括：

- execution gate fail-closed；
- exact profile mismatch；
- safe composer write/read-back；
- duplicate-send guard；
- conservative response completion；
- compact response baseline；
- response timeout resume without resend；
- Checker/Git digest；
- true CHECK failure promotion；
- CHECKED idempotent recovery；
- REVIEW_REQUIRED sticky boundary；
- PASS → Rolling Context delta；
- next Task refreshes current context；
- bounded multi-Task loop；
- deterministic NONE auto-run；
- deterministic failure does not promote or auto-retry；
- `run` / `resume` fail-closed CLI behavior。

这不是 Windows ChatGPT 真机验收。真实 UIA selector/model/effort/composer/response labels 仍需用户以后在目标客户端上校准一次。
