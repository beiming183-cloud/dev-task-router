# V1.0 — Release Readiness Candidate

V1.0 的目标不是继续扩大功能面，而是把 V0.7–V0.9 的 same-conversation 本地执行链收敛成一个**不会把自动测试、配置存在或 AI 自述误当成真机验收**的正式发布门禁。

当前状态：**自动可验证代码已进入 V1.0 readiness candidate；Windows ChatGPT 真机校准仍待完成，因此不能称为 V1.0 正式发布。**

## 1. 三层 Readiness

V1.0 不使用一个含糊的 `ready=true`，而是分开报告：

```text
automated_ready
live_windows_ready
release_ready = automated_ready && live_windows_ready
```

### automated_ready

检查：

- plan / LOW-MEDIUM-HIGH Chat routes 可解析；
- durable runtime audit 没有数据损坏；
- execution evidence hash chain、session / response digest / dispatch identity 等自动一致性检查可通过。

Linux CI 只能证明这一层。

### live_windows_ready

必须在目标 Windows ChatGPT build 上有真实证据：

- 当前 UI fingerprint 与校准 baseline 一致；
- model / effort / composer / Send / response selectors 已实际校准；
- LOW / MEDIUM / HIGH exact switch 都返回真实 `verified=true`；
- 三档都存在真实 dispatch → response → Checker PASS 的 end-to-end evidence；
- 需要独立 Review 的 Task 还必须有 Reviewer PASS。

### release_ready

只有两层同时满足才允许称为正式 V1.0 ready。

## 2. Privacy-safe UI Fingerprint / Drift Guard

V1.0 增加 `UIFingerprint`，只跟踪本项目真正依赖的 selector 类别，例如：

```text
mode selector
family / effort / verify labels
composer
Send
busy / response controls
```

不会把聊天正文、动态消息文本或整棵 UI tree 当 fingerprint。

一旦用户记录 baseline，真实 mode switch 前会先执行 drift guard：

```text
baseline absent → 保持旧 exact-switch verification 语义
baseline match  → 允许继续
baseline drift  → fail closed，停止点击
probe failed    → infrastructure failure，停止点击
```

UI drift 不增加 Task attempt，也不会触发 LOW → MEDIUM → HIGH。

CLI：

```text
autodev-readiness fingerprint --json
autodev-readiness fingerprint --record --json
```

## 3. Live Profile Calibration

`.autodev/profile-calibration.json` 只接受真实 `SwitchResult.verified=True`。

不能通过“requested profile”或手写配置制造已验证状态。每条 LOW / MEDIUM / HIGH 记录都绑定当前 UI fingerprint；UI build 变化后旧校准自动变 stale。

CLI：

```text
autodev-mode calibrate-profile LOW
autodev-mode calibrate-profile MEDIUM
autodev-mode calibrate-profile HIGH
```

该命令没有 dry-run 伪成功路径。

## 4. End-to-End Calibration 不能由 Registry 自证

`end_to_end_verified=true` 不是 release gate 的唯一依据。Readiness 会反查 durable execution evidence：

```text
SUBMITTED
→ RESPONSE_COLLECTED
→ CHECKED(ok=true)
→ STATE_RECORDED(PASSED)
```

并交叉核验：

- evidence SHA-256 chain；
- dispatch id；
- local session；
- response path / digest；
- requested profile 与 calibration profile；
- Review Task 的 `REVIEWED: PASS`。

缺任一关键边界都不能算 live end-to-end calibration。

## 5. Deterministic NONE → 独立 Debug Task → 原命令复验

V1.0 把 V0.8 的 `DEBUG_TASK_REQUIRED` 补成完整 UX。

失败仍严格保持：

```text
NONE command fails
→ source NONE Task remains FAILED
→ materialize independent debug candidate
→ explicit activation
→ debug Task independently classified
→ debug Task verified PASS
→ reopen source as PENDING
→ rerun original NONE command/check
```

关键约束：

- 原 NONE Task 永远不会被偷偷改成 LOW / MEDIUM / HIGH；
- debug candidate 不允许预设 `level/model`；
- activation 只允许**追加** Task，不允许删除已有 durable Task state；
- debug Task 插到 source 前面，因此项目 loop 先修复，再自然回到原 deterministic command；
- source 原有 attempts / failures / route history 全部保留；
- debug PASS 只会重新开放 source，不会伪造 source PASS；
- source 必须再次执行原命令/check 才能最终 PASS。

CLI：

```text
autodev-readiness debug-task --task-id <source> --json
autodev-local activate-debug <source> --json
autodev-local continue --max-cycles 10 --json
```

新增 evidence：

```text
DEBUG_TASK_MATERIALIZED
DEBUG_TASK_ACTIVATED
DEBUG_SOURCE_REOPENED
DETERMINISTIC_STARTED
DETERMINISTIC_CHECKED
```

## 6. Usage / Time / Token / Difficulty Outcome Calibration

V1.0 开始把真实执行结果沉淀成描述性证据，用于以后判断是否存在无意义 HIGH，但**不会在样本不足时自动降档**。

`.autodev/usage.jsonl` 现在可记录：

```text
attempt / phase / level / provider / model / executor
status / failure_type / returncode
duration_seconds
dispatch_id / source
input_tokens / output_tokens
usage_id
```

规则：

- deterministic NONE 使用 monotonic clock 记录真实 command/check elapsed time；
- model Task 使用 durable session 的 wall-clock execution window；
- `usage_id` 防止 crash/replay 重复计量；
- UI execution 拿不到 token 时必须保持 `null`，禁止估算成“真实 token”；
- provider/API 后端未来若返回真实 usage，才写 token 字段。

`autodev-readiness calibration` 按初始难度汇总：

- tasks / pass / fail / blocked；
- attempts / average attempts；
- one-shot pass；
- duration coverage / elapsed time；
- token coverage / reported token totals；
- promotion count；
- HIGH-first 与 promoted-to-HIGH；
- deterministic debug-required。

对于 `HIGH-first + one implementation attempt + PASS`，报告只生成 `high_manual_review_candidates`，其语义是：

> 值得未来做受控 lower-profile 对照实验。

它**不表示 MEDIUM/LOW 一定能完成，也不会修改 Task、Router、threshold 或 policy**。

Calibration 本身是只读的；生成报告不会刷新 workflow `updated_at`，也不会初始化缺失 Task state。

## 7. Readiness CLI

```text
autodev-readiness calibration --json
autodev-readiness readiness --json
```

在目标 Windows 上才使用：

```text
autodev-readiness readiness --probe-ui --json
```

不带 `--probe-ui` 时，已有 baseline 也只会报告 live UI 未在本次运行中验证，不会把旧证据冒充当前客户端状态。

## 9. 正式 V1.0 Release Gate

正式发布前仍必须完成一次目标 Windows 真机验收：

```text
[ ] record current privacy-safe UI fingerprint
[ ] verify selector drift = MATCH
[ ] LOW exact switch verified
[ ] MEDIUM exact switch verified
[ ] HIGH exact switch verified
[ ] composer write/read-back verified
[ ] Send verified
[ ] response completion selector verified
[ ] LOW end-to-end PASS evidence
[ ] MEDIUM end-to-end PASS evidence
[ ] HIGH end-to-end PASS evidence
[ ] autodev-readiness readiness --probe-ui => release_ready=true
```

因此在这一步完成前：

- PR 保持 Draft；
- package/plugin 不提前冒充正式 `1.0.0` 发布；
- 文档使用 **readiness candidate**，不用“V1.0 已完成”。

## 10. V1.0 之后

不作为当前正式发布阻塞项：

- cloud exact mode switching；
- 自建服务；
- 多用户 orchestration；
- VS Code UI；
- Agent Swarm；
- provider-specific token optimization；
- 根据足够真实样本进行可审计的 threshold tuning / controlled A-B calibration。

V1.0 先把一个边界做稳：**同一个复杂项目、同一个 canonical conversation、按真实 Task 难度切换 reasoning profile，并且任何“完成”都能追溯到实际 profile、response、Checker、Review、Git/evidence。**
